# Issue #716 — Sender-side KV Restore Trace (revised after t2 review)

## Context
Engine logs `state_seq_set_data: error loading state: unexpectedly reached end of buffer`
~13ms after STATE_PUT starts, on every save→restore cycle.

## t2 Review Finding
**Root-cause claim REJECTED**: .NET's `SocketPal.Unix.TryCompleteSendTo` loops
internally on `send()` — `NetworkStream.WriteAsync` does NOT complete with partial
counts on healthy connections. Physics also refutes it: 650MB truncated in 13ms =
>50GB/s, impossible on virtio.

**Revised scope**: This PR is instrumentation + typed failure handling. The real
root cause is likely Store-side truncation (see diagnostic below).

## What Changed (revision)

1. **RpcShortWriteException** (new typed exception in Hydra.Shared):
   - Properties: `Op`, `Declared`, `Written`, `TotalShortWrites`
   - Thrown from `WriteExactlyAsync` on `sent == 0` (peer EOF)
   - Caught by type in `WorkerSchedulerV2` and `WorkerSchedulerService`

2. **Store-side diagnostic** (the key addition):
   - V2 path: `RestoreRunner.RunAsync` logs ERR when `kv.Length != req.KvBytes`
   - Legacy path: `RestoreKvAsync` logs ERR when `restoreBlob.Length != item.KvBytes`
   - Chunks path: `RestoreKvAsync` logs ERR when assembled size != manifest totalSize
   - On a healthy path, sizes match → no warning emitted

3. **Removed dead code**: The `if (written != declaredPayloadLen)` check in
   `SendRequestAsync` was unreachable (WriteExactlyAsync can only return
   data.Length or throw). Replaced with pre-write parity invariant.

## What the Store Diagnostic Will Tell Us
In the live 6-turn A/B, the `restore_store_size_mismatch` log line will fire
every turn if the Store is returning fewer bytes than were saved. This directly
confirms or rules out Store-side truncation as the root cause. If sizes match
in the Store diagnostic but the engine still sees truncation, the problem is
in the StatePut framing between coordinator and engine (a separate fork-side
investigation).
